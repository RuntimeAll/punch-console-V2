### 0.2 它的确定性是"设计保证"还是"事后堆闸"？——**主体是事后堆闸**

四条铁证：

1. **表格在第①步就被拍平，全流程没有表格数据结构。**
   `parse_docx.py:138` / `parse_docx2.py:77` 都是 `for p in body.iter(W+'p')` —— 只遍历 `w:p`，表格里的段落被**当成普通段落**混进段落流，`w:tbl` 的行列关系当场蒸发。
   后果：12 本书**所有**表格（二上 29 张 / 一下 25 张 / 四下 13 张 …）都是**录完之后回源 docx 重建**的（`tbl_full_audit.py`、`mt_build_any.py`、`_tbl_extract.py`、各书 `f3*.py`）。
2. **行内图位置也在第①步丢，11 本书录完才发现。**
   README §16.1：老 `parse_docx.py` 只给公式发 token，非公式 PNG「在文本流里没有任何占位——位置信息在第①步就丢了」；§16.5 原话：「丢了以后全链路无感：split 正常、ingest 正常、渲染"也有图"——只有对照原书才发现图错位，**全书录完才发现＝修复成本 ×11 本**」。
3. **选项在录入期口径就是"不拆"。**
   README §3 末行：「选项内嵌题干（沿用上一战役口径，**不拆 option 块**）」。`ingest_unit_rb.py:111-116 build_block_json()` 只产 `text` 行 + `image` 行，**一个 option 块都不产、一个 table 块都不产**。
   后果：一下 52 题、四下 30 题、二上 23 题… 全部靠事后 F1 战役返修（一下记录 §总账、四下记录 §各类命中）。
4. **preflight 闸是 2026-07-23 才落地的，那时 12 本书 7349 题已经录完。**
   总纲 §3 实绩：一上闸后扫出 462 条违例，机器清了 444 条，剩 37 条 HARD 要人裁。闸是**追着已录数据跑**的。

### 0.3 但有三样东西是真正的"设计保证"，v2 应直接继承其思想

| 资产 | 是什么 | 位置 |
|---|---|---|
| **四道闸底座** | G1 schema / G2 可见字符多重集守恒 / G3 图 URL 多重集守恒 / G4 备份已存在；`dry→回源→apply` 三段 | `_work_1x/apply_lib.py:100-135`（`gate_check`） |
| **born_correct 整形+账** | 录入期整形器：6 条规则 + 守恒自检，**每条规则造成的可见字符增删必须显式登记进 ledger**，「净增删 − 登记增删 = 余量必空」，否则 `balanced=False`；越界即回退该改动并登记 error，绝不静默 mangle | `born_correct.py:2-28`（docstring）、`:288`（自检） |
| **判型→模板→校验三合一** | `classify_stem` 判型 / `format_*` 产标准结构 / `validate_block` 校验，同一份指纹表 | `qtype_fingerprint.py:45-63,151-212` |

> 🔴 一句话给 v2：**老区最贵的教训不是某条判据，是"信息一旦在最靠源头的一步丢掉，下游全链路无感"**（README §16.5）。v2 的块流 + 图在原位 + 图片守恒闸，方向已经对了；本清单的价值在于把老区那些"事后才补上的结构"（表格 / option / 图宽 / 上下标）**前移进第①步**。

### 0.4 🔴 重要发现：老区其实有 **三条互不兼容的 docx 链**

调查中确认，老区在 docx 录入上并存三套实现，**同一份 docx 走不同链会得到不同文本**：

| 链 | 入口 | 谁在用 | 表格 | 公式 | 上下标 | tab/br |
|---|---|---|---|---|---|---|
| **A. 录书管线**（本文 §1-§4 主体） | `parse_docx.py` / `parse_docx2.py`（标准库 XML） | 12 本整书教辅战役 | ❌ 拍平（`:138` 只遍历 `w:p`） | MathType WMF→PNG→**人工读图抄 LaTeX** | ❌ 不读 | ✅ `w:tab`→`\t`、`w:br`→`\n`（`:124-127`） |
| **B. teacher-mcp 卷子线** | `docconv.py docx_to_text()` → `paperparse.py` | `convert_doc` / `parse_paper_text` MCP 工具 | ❌❌ **整张表 0 输出**（见 1.2-⑮） | **dwml** OMML→LaTeX（`docconv.py:12-33`） | ❌ 不读（`:44-47` 连属性都不读） | ❌❌ **`w:tab` 零输出、`w:br` 静默丢** |
| **C. teacher-mcp 讲义线** | `lectureconv.py`（python-docx） | `convert_lecture_docx` | ⚠️ 读，但合并单元格=**内容重复** | dwml + 二级降级捞 `m:t` | ❌ 不读（`:73-93` 只读 text/bold/italic/color） | ⚠️ 靠 python-docx 隐式映射 |

**三条链的口径冲突是可复现的数据缺陷，不是理论风险**，最典型一处：

> `docconv.py:66` 给 MathType 公式产占位 `〖公式图:rId7〗` / `〖公式〗`；
> 而下游 `paperparse.py:18-19` 的 `FIG = 〖图(?::[^〗]*)?〗` / `FIG_IDS = 〖图:([^〗]*)〗` **要求字面 `〖图`**（`〖公式图` 的第二个字是"公"，不匹配）；
> `data_qbank.py:451` 的进入闸又是 `if "〖图" in stem_md` —— `"〖公式图"` 不含子串 `"〖图"`。
> ⟹ MathType 公式题的 `has_fig` **恒为 False**（`paperparse.py:172`，人工核对时 digest 里没 🖼 不会去看图）、`〖公式图:rId7〗` **既不成图也永不被清理**，原样进 `stem_text` 并参与 `dedup_key` 归一化。

🔴 **给 v2 的直接指令**：v2 必须只有**一个**切割器（`切割.py` 的 `cut_document()`），三条链的教训合并吸收，**绝不为"卷子/讲义/整书"各写一份**。参数化差异只在前面的分流与后面的归属。这条已写进 §7-③。
